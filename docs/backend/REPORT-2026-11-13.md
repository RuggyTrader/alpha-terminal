## 4. Financial accounting audit

- SOLANA and BITCOIN allocations split across their ACTIVE registered bots in integer micro-USD; original remainder/duplicate-request tests retained. No bot borrows another wallet's cash.
- Entry fees/collateral must fit the same bot wallet. Venue minima and eight-decimal increments are retained. The existing reduce-to-fit regression, engine acceptance matrix and real local Worker tests remain release gates.
- Fully collateralized SHORT reserves entry notional and never credits restricted proceeds as spendable funds. A loss beyond cash creates a liability; MAIN and other bots do not fund it.
- Fee benchmark remains 0.20% on every new bot fill. Legacy fee-free records and historical cost profiles are not rewritten.
- Positive realized **net** is swept once, in the closing batch. Permanent fault injection interrupts after sweep wallet changes and before the transfer journal completes; every financial row rolls back. Retrying settles once. Racing close ids produce one exit and exactly two sweep legs.
- Book identity remains `available + reserved = net funding + paid realized − fees`. Economic account equity additionally subtracts unpaid shortfalls and adds last-recorded UPL. Internal allocations/sweeps cancel across wallets. A sweep is not additional profit.
- The 5,003-trade fixture validates complete aggregation, legacy+bot scope, wins/losses and closed-trade drawdown. Open fees still reduce cash/equity immediately; closed-trade performance includes only closed trades.

No production balances, fills or reconciliation were inspected; all financial scenarios use clearly labelled local TEST funding/quotes.

## 5. Trading execution and reliability findings

The existing broker emulator's limit-touch/one-tick-through, improvement, gap and intrabar ordering tests, break-even/trailing tests, restart/outbox/duplicate tests and permanent TradingView parity gate are retained. No original signal rules, stop logic, TP2 or trading-hour restrictions changed.

**Important model boundary:** funded PAPER currently resolves orders in the engine's candle emulator and records them in D1 at the live Kraken ticker on message arrival. It does not submit real exchange resting limits. Pending limit state, age and cancellation are engine state/heartbeat metadata; D1 `bot_orders` represents submitted accepted/rejected actions, not an exchange order book or reserved pending order.

Consequently funded fills can differ from strategy limit prices (including beyond a nominal limit); gaps, message latency, same-candle entry/exit and stop decisions are not a tick-accurate exchange simulation. Capital and stop-risk reductions improve financial bounds without claiming limit-price guarantees. True exchange-style reservation, price-limited execution and durable pending-order lifecycle require an additive coordinated engine/Worker contract. They were not silently substituted into the verified strategy.

Existing failure isolation, per-bot state/locks, retry-safe outbox, restart recovery, gap handling and optional Alpaca request timeouts are preserved. No paid API or new service was added. Actual Windows launcher behavior and production uptime are not verified here.

The existing meter does not obtain row/duration metadata from `.first()` or `.raw()`. Therefore all displayed row totals and D1 duration totals are **lower bounds**. In particular the performance endpoint's reported row count does not mean its lifetime query scanned only one row. The raw measurement file and tool now carry that limitation explicitly. Production billing/CPU estimates cannot be inferred from these partial counters.

The lifetime query scans complete closed history and computes a windowed equity curve in SQLite; cost grows with history. At larger histories, measure complete D1 metadata and consider an additive materialized summary/checkpoint design. No paid infrastructure was introduced.

The prior per-candle estimate is not a polling estimate. Source review shows a synced funded bot can read the ledger in `prepareSizing`, read again in `verifyLedger`, and post a heartbeat **every poll**, even without a new candle. With four bots and the default 20-second sleep, a loose upper bound excluding round duration is 4,320 rounds/day × 4 × 3 = **51,840 core engine requests/day**, before mirror, orders, notifications and dashboard requests. The actual loop adds inter-bot pauses and network time, so this is not measured usage. Heartbeats can approach 17,280/day under the same upper bound, plus other writes; the four bots also have four distinct symbol/timeframe feeds, so their per-round candle cache does not collapse these four into one provider request. Do not rely on the earlier approximately 7,000/day per-candle projection as a measured free-tier guarantee.

Existing optional Alpaca requests remain bounded at 3.5 seconds and Kraken quote requests at 5 seconds. Credential-free local measurements exercise the not-configured fallback, not a production Alpaca outage. Production CPU, complete D1 rows, real polling traffic and uptime remain unmeasured.
